# 核心数据解析及映射说明

> 本文档为《[关键技术难点与核心原理说明](./关键技术难点与核心原理说明.md)》中 **1. 数据解析融合逻辑** 的详细展开，供 PPT/汇报深挖实现时引用。

本文档说明 AppThinnerAnalyzer 中**三源数据**（LinkMap、IPA/App 包、工程目录）的解析方式，以及**工程路径与包内路径的映射规则**，用于在统一视图（TreeMap、按目录/按模块）上正确归属代码体积与资源体积。

---

## 1. 三源数据与目标

| 数据源 | 产出 | 用途 |
|--------|------|------|
| **LinkMap** | 每个编译单元（.o）的代码体积 + 符号明细；需匹配到**工程相对路径** | 代码维度大小（CodeSizeInfo） |
| **IPA / .app** | 包内所有文件的路径、大小、类型（代码/资源/动态库） | 资源与动态库体积；与工程路径映射后填到树节点 |
| **工程目录** | 项目下所有文件列表（代码+资源）的**相对路径** | 树骨架；PathMapping 的「工程侧」 |

**目标**：建立「工程相对路径 ↔ 包内相对路径」的映射表，使 TreeMap 以工程路径为键，代码大小来自 LinkMap，资源/动态库大小来自 IPA 经映射后聚合。

---

## 2. LinkMap 解析

### 2.1 文件结构

- **`# Object files:`**：每行 `[编号] 路径`，路径可为 `.o`、`.../Name.framework/Name(Obj.o)`、`.../libX.a(Obj.o)` 或 `.../libX.a[N](Obj.o)`（方括号为归档成员索引）。
- **`# Symbols:`**：每行 `地址 大小 文件编号 符号名`，大小为单位字节（十六进制）。

### 2.2 解析流程（LinkmapAnalyzer）

1. **逐行解析**：识别当前段（Object files / Symbols）；进入 Object files 时解析每行为 `ObjectFileInfo(index, filePath, fileName, totalSize=0)` 并建立编号→Object 字典。
2. **Symbols 段累加**：每解析一条符号，根据**文件编号**找到对应 Object，将该符号的 `size` 累加到该 Object 的 `totalSize`。由此得到每个编译单元的真实代码体积。
3. **产出**：`LinkmapParseResult(objectFileInfos, symbols)`。`SymbolInfo` 含 `objectFileIndex`，便于按文件查看符号分布。

### 2.3 路径规范化与 LTO

- **前缀剥离**：对 linkmap 中的绝对路径，若以配置的前缀开头（如 `/Volumes/data/workspace/`、`/Users/.../DerivedData/`），则去掉该前缀，得到更接近项目根的相对形式。
- **通用规则**：若未匹配到配置前缀，则尝试去掉路径中 **`DerivedData/` 及其之前部分**，便于跨机器展示。
- **LTO/thinlto**：开启 LTO 后 Object 可能为 `*.thinlto.o`，路径与工程源文件不一致，需通过「对象基名 / 静态库名」匹配到工程路径（见 2.4）。

### 2.4 从 LinkMap 路径到工程路径（LinkmapPathAdapter）

**入口**：`LinkmapAnalyzer.mapObjectFilesToProjectStructure(parseResult:projectFileIndex:projectFileEntries:linkmapPathPrefixesToStrip:)`。对每个 `ObjectFileInfo` 先做 `normalizeLinkmapPathForMatching`（去掉 `Release-iphoneos` 及之前、去掉 `XCFrameworkIntermediates/` 前缀），再调用 `LinkmapPathAdapter.resolveToProjectPath(linkmapObjectPath:fileName:)` 得到 `(resolved, isMapped)`，产出 `CodeSizeInfo(relativePath: resolved, fileName, totalSize, symbols)`。**未映射**时仍写入 CodeSizeInfo，`relativePath` 为剥离前缀后的 linkmap 路径，便于在树中展示并统计未映射体积。

**匹配优先级**（Adapter 内）：

1. **静态库**：路径含 `.a(Obj.o)` 或 `.a[N](Obj.o)` 时，解析**库名**（如 `libX.a`→`X`）与**对象基名**（括号内 `.o` 的基名）。用预构建的 `staticLibLookup["pathComponent|baseName"]` 或 `staticLibNameToPath[库名]` 查找项目路径；命中则返回（优先于仅按基名查，避免与主 Target 同名文件混淆）。
2. **Framework**：路径含 `.framework/` 时，用 `frameworkNameToPath`（framework 名小写 → 项目中 .framework 目录相对路径）将 `XXX.framework/XXX(Obj.o)` 整体映射到项目 .framework 目录。
3. **按对象基名查 projectFileIndex**：从括号内或 fileName 取基名，在 `projectFileIndex[基名]` 中取候选路径（多候选时取第一个）。
4. **按完整 fileName 查 projectFileIndex**：兼容未带括号的写法。
5. **回退**：返回经前缀剥离（`pathPrefixesToStrip` 或 DerivedData 通用剥离）后的 linkmap 路径。

**projectFileIndex**：由 `LinkmapAnalyzer.makeProjectFileIndex(from: projectFileEntries)` 从工程全量文件列表构建，key 为**文件名小写**或**基名小写**，value 为该项目相对路径列表。**staticLibLookup**（key=`pathComponent|baseName`）、**staticLibNameToPath**（库名→路径）、**frameworkNameToPath**（framework 名→.framework 目录路径）均由 `projectFileEntries` 预构建，用于 O(1) 查找。

## 3. IPA / App 包解析

### 3.1 入口与结构

- **IPA**：zip 格式，解压到临时目录后定位 **Payload/xxx.app**（或根下 .app）；再对 .app 做递归枚举。
- **.app 直接选择**：不解压，直接对所选 .app 目录递归枚举。

### 3.2 .app 内枚举（PackageParser.parseAppBundle）

- **递归遍历**：使用 `FileManager.default.enumerator` 遍历 .app 内所有文件（含子目录），跳过目录本身，只处理文件。
- **相对路径**：以 .app 根为基准，`relativePath = fileURL.path.dropFirst(bundleBasePath.count + 1)`，即包内相对路径（如 `Frameworks/XXX.framework/XXX`、`Assets.car`、`Info.plist`）。
- **主可执行文件**：从 .app 根目录 `Info.plist` 读取 `CFBundleExecutable`，与根目录下无子路径的文件名比较，相等则标记 `isMainExecutable = true`，用于正确归属主二进制代码体积。

### 3.3 文件类型（determineFileType）

| 类型 | 判定 | 说明 |
|------|------|------|
| **Code** | 扩展名 .swift/.m/.mm/.h/.cpp/.c 等，或 contentType 为 sourceCode | 主二进制（无扩展名且在根目录）也归为 code |
| **Resource** | 扩展名 .png/.jpg/.mp3/.mp4/.json/.plist/.storyboard/.xib/.xcassets 等，或 contentType 为 image/audio/video/data | 图片、音频、视频、配置、界面资源等 |
| **Framework** | 扩展名 **.framework / .dylib / .a** | 动态库或静态库在包内的产物 |
| **Other** | 其余 | 如部分插件或未知格式 |

即：**动态库**（.framework、.dylib）与**静态库**（.a）在包内统一识别为 `fileType == .framework`；其余按扩展名/ContentType 归为 code 或 resource。

### 3.4 产出

- **PackageParseResult**：`packageFiles: [PackageFileInfo]`，`appBundlePath`（.app 的 URL），`tempDirectoryForCleanup`（仅 IPA 解压时非 nil，由调用方在分析结束后清理）。
- **PackageFileInfo**：`relativePath`（包内相对路径）、`fileName`、`size`、`fileType`（code / resource / framework / other）、`isMainExecutable`。

包内**动态库与资源**均在此列表中，通过后续 **PathMapping** 与工程路径对应，用于 TreeMap 上资源/框架体积的归属。

## 4. 工程目录解析（树骨架）

- **ProjectResourceScanner.scanProjectDirectoryAllFiles(at:)**：扫描项目目录下**所有文件**（代码+资源），排除构建产物与常见忽略目录（如 Pods、Carthage、.build、DerivedData 等），产出 `[ProjectFileEntry]`（relativePath、fileName、size、isSourceCode、resourceType）。
- **同模块**：`scanProjectDirectory(at:)` 内部调用 `scanProjectDirectoryAllFiles`；`buildPathMappingTable(projectPath:packageFiles:)` 先 `scanProjectDirectory` 再调用 PathMappingResolver 的建表逻辑（用于需完整 PathMappingResult 的场景）。
- **作用**：  
  - 作为 **树骨架** 的路径集合（与 LinkMap、IPA 融合时以工程路径为键）；  
  - 作为 **资源/框架体积分配** 的工程侧：在 `buildPathToResourceSize` / `buildPathToFrameworkSize` 中按 fileName 与路径相似度将包内 size 归到工程路径；  
  - 用于 **LinkmapPathAdapter** 的 projectFileIndex、staticLibLookup、staticLibNameToPath、frameworkNameToPath。

## 5. 工程路径与包路径的映射（资源/框架体积归属）

### 5.1 主流程中的归属方式（buildIntegratedDataFromProjectEntries 内）

整合阶段**不**依赖独立的 PathMappingResult，而是在 `AnalysisService` 内通过以下两步将包内体积归到工程路径：

- **资源体积**（`buildPathToResourceSize`）：  
  - **非 Assets.car**：`buildPathToPackageSize(projectFileEntries, packageFiles)` — 按 **fileName** 分组（`packageByFileName`、`projectEntriesByFileName`），采用「按 .app 路径驱动」：同名时按包路径从长到短排序，为每条包路径在未分配的工程候选中选**得分最高**者（`packageToProjectScore`：路径尾部相似度 `pathSimilarity` + 若工程路径包含包路径首段如 `WSResources.bundle` 则加 1000 分），一对一分配 size。  
  - **Assets.car**：当提供 `appBundlePath` 时，调用 `assetutil -I` 解析 .car，按 **asset 名** 与工程侧 `assetNameToPaths`（.imageset/.colorset/.dataset 文件夹名及 @2x 等逻辑名）匹配，将解析出的资源体积归到对应工程路径；未匹配部分记为虚拟节点（如 `Pods/库名/Assets.car 未匹配`）避免遗漏体积。
- **框架体积**（`buildPathToFrameworkSize`）：将 .app 内 `Frameworks/` 下按 **.framework bundle** 聚合为 `frameworkBundleToSize`；对每条工程条目，用「工程路径是否包含该 bundle 名」（不区分大小写）匹配，每个 bundle 只计入一个工程条目，避免重复。

### 5.2 PathMappingResolver（独立映射服务）

当需要**完整映射表**（mappings、conflicts、unmappedFiles、accuracyReport）时，使用 `PathMappingResolver.resolvePathMappings(projectPath:packageFiles:linkmapSymbols:projectResources:)`：

- **Step 1**：若传入 `projectResources` 则直接 `buildInitialMappingTable(projectResources, packageFiles)`；否则调用 `ProjectResourceScanner.buildPathMappingTable(projectPath, packageFiles)`（内部先 `scanProjectDirectory` 再建表）。
- **Step 2**：`enhanceMappingWithSymbols`：用 linkmap 符号的 fileName 辅助解析 unmapped，加入 mappings 并更新 accuracy。
- **Step 3**：`resolveConflicts`：对多候选冲突用路径结构相似度 + 大小相关性 + 目录上下文加权，得到 PathMappingResolution。
- **Step 4**：`generateMappingAccuracyReport` 产出 accuracyReport。

该结果可用于报告、对比或 `performIntelligentMapping` 等场景；主分析流水线中的资源/框架归属见 5.1。

### 5.3 初始建表（buildInitialMappingTable）

- **输入**：`projectResources`、`packageFiles`。
- **步骤**：`packageFiles` 按 fileName 分组；遍历工程文件，按 fileName 找包内候选；无候选→unmappedFiles，唯一候选→mappings，多候选→路径结构相似度选最佳并记录 PathMappingConflict。
- **路径结构相似度**（calculatePathStructureSimilarity）：从路径末尾向前加权，相同组分越多、越靠近文件名分数越高，0~1。

### 5.4 冲突解析（resolveConflicts / resolveIndividualConflict）

- 路径结构相似度（0.5）+ 大小相关性（0.3）+ 目录上下文（0.2），取加权分最高候选，得到 PathMappingResolution(selectedPath, confidence, reasoning)。

## 6. 三源融合与数据流小结

```
LinkMap  ──解析──► ObjectFileInfo[] + Symbols
         ──normalizeLinkmapPathForMatching + LinkmapPathAdapter.resolveToProjectPath──► CodeSizeInfo[](relativePath, totalSize, symbols)
         ──按 isVirtualObjectPath(relativePath 含 "(") 分组──► virtualObjectEntries / realCodeEntries
                                                                     │
工程目录 ──scanProjectDirectoryAllFiles──► ProjectFileEntry[] ────────┼──► 树骨架
                                                                     │
IPA/.app ──parseAppBundle──► PackageFileInfo[] ──buildPathToResourceSize（fileName+路径得分 + .car 解析）──► pathToResourceSize
         ──buildFrameworkBundleToSize──► frameworkBundleToSize ──buildPathToFrameworkSize──► pathToFrameworkSize
                                         │
                                         ▼
整合 buildIntegratedDataFromProjectEntries：
  • pathToCodeSize：仅对 realCodeEntries 按 relativePath 聚合 totalSize，再 aggregateFrameworkObjectPathsToBinary（.o 归到主二进制等）
  • 每条 projectFileEntry：resourceSize ← pathToResourceSize，frameworkSize ← pathToFrameworkSize，codeSize ← pathToCodeSize；若 frameworkSize>0 则 codeSize=0；若为「被虚拟 .o 覆盖的容器」则 frameworkSize=0
  • 虚拟 .o 节点：由 virtualObjectEntries 生成 IntegratedFileInfo（relativePath 含 "(")，追加到 files）
  • .car 未匹配体积：追加虚拟节点（如 Pods/库名/Assets.car 未匹配）
  ► IntegratedAnalysisData(files, summary)
```

- **虚拟 .o 节点**：LinkMap 中 `.framework/Name(Obj.o)` 或 `.a(Obj.o)` 经 Adapter 解析后 relativePath 可能保留括号形式（如 `Pods/X.framework/X(Foo.o)`），在整合时视为「虚拟」节点单独成行，不参与 pathToCodeSize 聚合；其体积由该编译单元 totalSize 承载，对应 .framework/.a 容器条目的 frameworkSize 置 0 避免重复。
- **动态库与资源**：IPA 解析阶段已区分为 fileType 的 .framework 或 .resource；资源与框架体积通过 5.1 的 fileName+路径得分与 .car 解析、frameworkBundleToSize 归属到工程路径，最终在 TreeMap 中按工程目录聚合展示。

## 7. 代码位置速查

## 8. 可选后续增强

- **LinkMap**：从配置或设置读取 `linkmapPathPrefixesToStrip`；多候选时按路径相似度或模块名排序选择。
- **IPA**：对 Assets.car 做进一步解析（若需按 asset 维度归属）；区分 .app 内 Frameworks 子目录与主二进制。
- **PathMapping**：unmapped 列表导出便于补充规则；resolveUsingSymbols 与 package 的对应逻辑可根据实际符号/包结构再细化。
- **报告**：对「仅包内有 / 仅工程有」的路径做统计或单独展示，便于核对映射完整性。

以上规则与流程已实现在 `AppThinnerAnalyzer` 的 `LinkmapAnalyzer`、`PackageParser`、`PathMappingResolver` 及 `AnalysisService` 中，形成完整的核心数据解析及映射链路。
