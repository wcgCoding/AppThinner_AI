# 分析配置选项开发计划

## 一、需求概述

在分析 TAB 中增加**分析配置**区域，通过开关控制三类扫描是否启用：

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| **代码重复扫描** | 启用后执行代码重复（Clone / 相似代码）分析 | 关 |
| **资源重复扫描** | 启用后执行资源重复（同名/同内容图片等）分析 | 关 |
| **Pods 库依赖扫描** | 启用后解析 Podfile/Podfile.lock，分析 Pods 依赖与体积 | 关 |

---

## 二、整体架构

- **配置存储**：应用级配置，使用 `UserDefaults` 持久化，下次启动保持用户选择。
- **配置传递**：`MainViewModel` 持有配置 → `startAnalysis(analysisOptions:)` → `AnalysisService.analyzeProject(..., analysisOptions:)`。
- **执行策略**：分析流程中根据 `analysisOptions` 的开关决定是否调用对应扫描服务；未实现前可先走「配置 + 透传」，扫描结果为占位/空，便于后续按项实现。

---

## 三、开发阶段

### 阶段 1：配置模型与 UI（不改变分析结果）

**目标**：增加配置数据结构、持久化、分析 TAB 上的三个开关，并把配置传入分析流程；分析逻辑暂不因开关而改变结果。

**任务清单**

1. **数据层**
   - 在 `DataModels.swift`（或新建 `AnalysisOptions.swift`）中定义：
     - `struct AnalysisOptions`：包含 `enableCodeDuplicateScan: Bool`、`enableResourceDuplicateScan: Bool`、`enablePodsDependencyScan: Bool`，并提供默认值（均为 `false`）。
   - 可选：若希望「每次分析」记录当时配置，可在 `AnalysisProject` 的 Core Data 中增加可选属性（如 JSON 或三个 Bool），用于历史记录与报告；本阶段可先不做。

2. **持久化**
   - 在 `MainViewModel`（或专用 `AnalysisOptionsStorage`）中：
     - 使用 `UserDefaults` 读写上述三个布尔值（key 如 `AppThinner.analysisOptions.enableCodeDuplicateScan` 等）。
     - 提供 `analysisOptions: AnalysisOptions`（get/set），set 时写回 UserDefaults。
   - App 启动时从 UserDefaults 加载，作为默认分析配置。

3. **UI**
   - 在 **分析 TAB**（`AnalysisView.swift`）中，在「Input Files」与「External Data」之间（或下方）增加 **「分析配置」** 区域：
     - 标题：「分析配置」或 “Analysis Options”。
     - 三个 `Toggle`：
       - 「启用代码重复扫描分析」
       - 「启用资源重复扫描分析」
       - 「启用 Pods 库依赖扫描分析」
     - 绑定到 `MainViewModel` 的 `analysisOptions`（或三个 `@Published` 布尔值，与 UserDefaults 同步）。

4. **串联**
   - `MainViewModel.startAnalysis`：无参调用时使用当前 `analysisOptions`；若已有重载，增加 `analysisOptions: AnalysisOptions? = nil`，内部取 `analysisOptions ?? self.analysisOptions`。
   - `AnalysisServiceProtocol` 与 `AnalysisService.analyzeProject`：增加参数 `analysisOptions: AnalysisOptions`（或可选，默认 `.default`）。
   - 在 `AnalysisService` 内：接收 `analysisOptions` 并保存到当前分析上下文（如 `buildUnusedContentResults` 所在流程）；本阶段仅在日志中打印当前配置，不改变现有无用类/资源等结果。

**验收**：分析 TAB 可见三个开关，开关状态持久化；点击「Start Analysis」后日志中能看出传入的配置；现有分析结果与未加配置前一致。

---

### 阶段 2：代码重复扫描

**目标**：当「启用代码重复扫描分析」为开时，在分析流程中执行代码重复检测，并产出可展示/导出的结果。

**任务清单**

1. **能力定义**
   - 明确「代码重复」范围：例如类/方法级克隆（Clone）、或文件级相似度（如基于 AST/Token 的相似代码块）。
   - 定义输出结构：如 `DuplicateCodeGroup`（多份相似代码的路径列表、相似度、建议合并说明等），并加入 `DataModels` 或专用模型。

2. **服务层**
   - 新增 `CodeDuplicateScanService`（或扩展现有 `CodeAnalyzer`）：
     - 输入：工程路径、需扫描的源码文件列表（可复用 `ProjectResourceScanner`/现有工程文件列表）。
     - 输出：`[DuplicateCodeGroup]`。
   - 实现方式可选：基于字符串/哈希的简单重复、或接入 AST/树相似度（若已有或引入轻量解析库）。

3. **与主流程对接**
   - 在 `AnalysisService.analyzeProject` 中，若 `analysisOptions.enableCodeDuplicateScan == true`：
     - 在合适阶段（如 Phase 2 与无用扫描并行或之后）调用代码重复扫描。
     - 将结果写入 `AnalysisProject` 或关联存储（若阶段 1 已为项目增加「分析配置/结果」扩展，此处写入代码重复结果）。
   - 若为 `false`，不调用、不写入。

4. **展示与导出**
   - 在「分析结果」或「可视化/优化」TAB 中增加「代码重复」入口（列表或汇总），展示各组重复及路径。
   - 报告/导出中包含代码重复摘要（如 HTML/JSON）。

**验收**：开启「代码重复扫描」并分析后，能看到代码重复结果；关闭则不执行、无该部分结果。

---

### 阶段 3：资源重复扫描

**目标**：当「启用资源重复扫描分析」为开时，执行资源重复（如图片同名/同内容、多份相同资源）检测。

**任务清单**

1. **能力定义**
   - 明确「资源重复」范围：同名资源、同内容（MD5/字节一致）资源、或两者结合。
   - 定义输出结构：如 `DuplicateResourceGroup`（路径列表、大小、建议保留/删除建议），加入 `DataModels` 或专用模型。

2. **服务层**
   - 新增 `ResourceDuplicateScanService`：
     - 输入：工程内资源文件列表（可复用 `ProjectResourceScanner` 扫描结果）、可选 IPA 内资源列表。
     - 输出：`[DuplicateResourceGroup]`。
   - 实现：按文件名分组；对同名前缀/同扩展名文件做内容哈希比对（抽样或全量，视性能取舍）。

3. **与主流程对接**
   - 在 `AnalysisService.analyzeProject` 中，若 `analysisOptions.enableResourceDuplicateScan == true`：
     - 在合适阶段调用资源重复扫描（可与工程扫描结果复用）。
     - 将结果写入项目或关联存储。
   - 若为 `false`，不调用、不写入。

4. **展示与导出**
   - 在结果界面增加「资源重复」列表/汇总。
   - 报告/导出中包含资源重复摘要。

**验收**：开启「资源重复扫描」后能看到重复资源组；关闭则无该部分。

---

### 阶段 4：Pods 库依赖扫描

**目标**：当「启用 Pods 库依赖扫描分析」为开时，解析 Podfile/Podfile.lock，并可选结合工程/IPA 体积，产出 Pods 依赖与体积视图。

**任务清单**

1. **能力定义**
   - 输入：工程根目录下的 `Podfile`、`Podfile.lock`（及可选 `Manifest.lock`）。
   - 输出：依赖列表（名称、版本、子依赖）、可选与 LinkMap/IPA 中 Pods 体积关联（当前工程已有 Pods 路径处理，可复用）。
   - 定义 `PodsDependencyInfo` 等模型（名称、版本、层级、预估体积等）。

2. **服务层**
   - 新增 `PodsDependencyScanService`（或 `PodfileParser` + 体积汇总）：
     - 解析 `Podfile.lock`（YAML 或正则提取 DEPENDENCIES、PODS、SPEC REPOS 等）。
     - 可选：与现有 LinkMap/包内 Pods 路径（如 `Pods/XXX/`）匹配，得到各 Pod 体积。
   - 依赖：仅 Foundation + 文件读取；YAML 解析可用系统或轻量库。

3. **与主流程对接**
   - 在 `AnalysisService.analyzeProject` 中，若 `analysisOptions.enablePodsDependencyScan == true` 且存在工程路径：
     - 在 Phase 1 或 Phase 2 中调用 Pods 依赖扫描（仅需工程路径 + 可选 packageFiles/codeSizeInfo）。
     - 将结果写入项目或关联存储。
   - 若为 `false` 或无工程路径，不调用。

4. **展示与导出**
   - 在结果界面增加「Pods 依赖」视图（树或表：依赖名、版本、体积占比）。
   - 报告/导出中包含 Pods 依赖与体积摘要。

**验收**：开启「Pods 库依赖扫描」且工程含 Podfile.lock 时，能看到依赖列表（及可选体积）；关闭则无该部分。

---

## 四、依赖与顺序

- **阶段 1** 为前置，独立于 2/3/4，优先落地。
- **阶段 2、3、4** 可并行开发，均依赖阶段 1 的 `AnalysisOptions` 与 `analyzeProject(..., analysisOptions:)` 透传。
- 若需在「分析结果」中统一展示三类结果，可在阶段 1 即预留「扩展结果」存储（如 Core Data 关联表或 JSON 字段），便于 2/3/4 写入。

---

## 五、文件与接口变更摘要

| 变更类型 | 文件/位置 |
|----------|------------|
| 新增模型 | `AnalysisOptions`（DataModels 或 AnalysisOptions.swift） |
| 持久化 | MainViewModel 或 AnalysisOptionsStorage + UserDefaults |
| UI | AnalysisView：新增「分析配置」区域与三个 Toggle |
| 协议 | AnalysisServiceProtocol：`analyzeProject(..., analysisOptions: AnalysisOptions)` |
| 实现 | AnalysisService：接收并依据 analysisOptions 分支调用（阶段 2/3/4 各增一次调用） |
| 新服务 | CodeDuplicateScanService、ResourceDuplicateScanService、PodsDependencyScanService（各阶段新增） |
| 结果模型 | DuplicateCodeGroup、DuplicateResourceGroup、PodsDependencyInfo（各阶段新增） |
| 展示 | 分析结果/可视化/报告：代码重复、资源重复、Pods 依赖三个子模块（各阶段新增） |

---

## 六、风险与注意点

- **性能**：代码/资源重复扫描可能耗时，建议在 Phase 2 中异步执行并通过 `progressUpdates` 反馈进度，必要时支持「仅扫描部分目录」或采样。
- **Pods 解析**：Podfile.lock 格式随 CocoaPods 版本可能微调，解析需兼容常见格式并做异常处理。
- **配置与历史**：若未来需「按某次分析时的配置」复现，可在阶段 1 或后续为 `AnalysisProject` 增加配置快照字段。

按上述阶段实施，即可在分析 TAB 中通过三个开关控制代码重复、资源重复、Pods 依赖三类分析的启用，并逐步交付可用的扫描与展示能力。
